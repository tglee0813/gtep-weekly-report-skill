# GTEP 주간업무보고서 작성

GTEP 요원이 협력업체별로 매주 작성하는 주간업무보고서를 일주일치 원자료로 채운다.
작성 순서는 항상 **① 공식 양식 복사·붙여넣기 → ② 날짜 기입 → ③ 캡처 내용으로 각 항목 기입**이다. 표를 새로 디자인하거나 직전 주차 표를 베끼지 않는다.
보고서 작성일은 항상 그 주 **금요일** 날짜로 적는다(5번 '작성일 규칙' 참고).
Claude와 Codex 어디서든 같은 순서로 진행한다. 도구 이름은 환경에 맞게 바꿔 쓴다.

## 공식 양식 (원본)

- 양식 문서: https://docs.google.com/document/d/1N8SYd-FPh-IlEeNMALeWM-6Vov4nB00mIgaxa4g4XBI/edit?tab=t.0 (문서 ID `1N8SYd-FPh-IlEeNMALeWM-6Vov4nB00mIgaxa4g4XBI`)
- 복사 대상: **6번째 항목 「VI . 주간업무보고서」** 아래, '(아래 부터 복사하여 누적 작성하시면 됩니다)' 다음에 있는 **첫 번째 `2026. 00. 00 주간업무보고서` 헤딩 + 바로 아래 10행×2열 표** 한 세트.
- 양식은 바뀔 수 있으므로 매번 원본을 다시 읽어 구조를 가져온다. 아래 '양식 구조'는 확인용 기준이며, 원본과 다르면 원본을 따르고 사용자에게 알린다.

### 양식 구조 (2026-10 기준)

헤딩 문단: `2026. 00. 00 주간업무보고서`, HEADING_1, 굵게 13pt, 남색 글자(RGB 0.12/0.22/0.39), 아래 테두리 1.5pt 남색, 위 10pt·아래 6pt 간격.

표: 10행 × 2열, 열 너비 105pt / 380pt 고정. 왼쪽 라벨 칸은 회색 배경(0.937), 굵게, 가운데 정렬, 세로 가운데.

| 행 | 왼쪽 라벨 | 오른쪽 칸 원래 내용 |
|---|---|---|
| 0 | 업무기간 | `2026.   .   ~ 2026.   .` |
| 1 | C/L 발송 횟수 | `주간 N회 / 누적 N회` + 회색 안내문(누적값은 [C/L 발송 관리] 시트…) |
| 2 | 활동 및 수행 업무 (두 칸 병합, 회색) | — |
| 3 | 정기업무 | 회색 안내문 '업무 성격별 진행사항 정리' |
| 4 | 전자상거래 업무 | 회색 안내문 '플랫폼별 진행사항 정리' |
| 5 | 전시회 관련 / (예정전시회) | `· 확정 전시회 :` / `· 일정 :` / `· 준비내용 및 진행사항 :` + 회색 안내문 |
| 6 | 주요 논의사항 | 빈칸 |
| 7 | C/L 발송 포맷 및 발송 현황 (두 칸 병합) | 회색 안내문 2줄, `1. 총 발송 횟수 : N회` / `2. C/L 발송 아이템 :` / `3. Inquiry 문의 : N회 / 총 N회` / 회색 안내문 / `(1) Inquiry 대상 :` / `(2) Inquiry 내용 :` |
| 8 | 다음주 업무계획 | 빈칸 |
| 9 | 애로 및 질의사항 | 빈칸 |

회색 안내문 = 9pt, 회색(0.549), 기울임 텍스트. 채울 때 지운다.

## 0. 입력 확인 (착수 전)

아래 자료가 있는지 확인하고, 빠진 것은 먼저 요청한다.

| 자료 | 용도 |
|---|---|
| 업체 톡방 캡처 (이번 주 분량) | 업체와의 논의·요청·회신 → 정기업무, 주요 논의사항 |
| 동료(공동 담당 요원) 대화 캡처 | 내부 논의·역할 분담·계획 → 주요 논의사항, 다음주 계획 |
| 주고받은 파일 (신청서, 보고서, 리스트 등) | 사실 확인, 수치·일정 근거 |
| To-Do / 빅플랜 / 지원사업 리스트 시트 링크 | 다음주 업무계획, 진행 현황 |
| 업체 보고서 문서 (Google Docs 링크 또는 파일) | 작성 대상 (양식을 붙여넣을 곳) |
| 업체 공유 폴더 (Drive 등) | 교차검증용 배경 자료 |

- 공식 양식 문서는 위 링크를 기본으로 쓴다. 사용자가 다른 양식 링크를 주면 그것을 쓴다.
- 첨부 이미지가 두 장 이상이면 **서로 같은 파일인지 먼저 확인**한다(해시 비교). 중복이면 바로 알리고 올바른 캡처를 요청한다.
- 업체명, 업무기간, 공동 담당자가 불분명하면 질문한다. 작성일은 묻지 않고 금요일 규칙으로 정한다.

## 1. 양식 복사·붙여넣기 (가장 먼저)

캡처를 읽기 전에, 업체 보고서 문서 맨 끝(직전 주차 표 다음)에 공식 양식 한 세트를 그대로 붙여넣어 둔다.

1. 양식 문서를 읽어 'VI . 주간업무보고서' 아래 첫 번째 `2026. 00. 00 주간업무보고서` 헤딩과 그 다음 표를 찾는다. 헤딩·각 셀의 텍스트와 서식(굵기, 크기, 색, 기울임, 정렬, 배경, 병합, 열 너비)을 확인한다.
2. 업체 문서에 이번 주 블록이 이미 있는지 확인한다. 이미 붙여넣은 빈 양식이 있으면 새로 붙이지 않고 그것을 채운다. 다음 주용 빈 양식 블록은 건드리지 않는다.
3. 업체 문서 끝에 같은 헤딩과 표를 재현한다(아래 '문서 반영' 참고). 라벨·고정 문구·회색 안내문까지 원본과 똑같이 넣고, 병합(2행, 7행)과 열 너비, 라벨 칸 회색 배경까지 맞춘다.
4. 헤딩이 새 페이지 맨 위에서 시작하도록 페이지 나누기를 건다(5번 '페이지 시작 위치').

Google Docs API에는 문서 간 복사 기능이 없으므로 '복사'는 원본 구조를 읽어 업체 문서에 똑같이 다시 만드는 것을 뜻한다. 사용자가 직접 붙여넣어 둔 경우에는 그 블록을 그대로 쓴다.

## 2. 날짜 기입

- 헤딩 `2026. 00. 00` → 그 주 금요일 `YYYY. MM. DD` (5번 '작성일 규칙').
- 업무기간 `2026.   .   ~ 2026.   .` → 직전 보고서 종료일 다음 날 ~ 이번 주 실제 업무 종료일. 첫 보고면 킥오프일부터. 작성일(금요일)과 같을 필요는 없다.

## 3. 자료 읽기

### 긴 캡처 이미지
세로로 긴 카톡 캡처는 한 번에 읽으면 글자가 뭉개진다. 약 900px 높이로 잘라 2배 확대한 뒤 순서대로 모두 읽는다.

```python
from PIL import Image
im = Image.open(path); w, h = im.size
for i, y in enumerate(range(0, h, 900)):
    c = im.crop((0, y, w, min(h, y + 950)))
    c.resize((c.width * 2, c.height * 2)).save(f"crop_{i:02d}.png")
```

- 날짜 구분선(예: 2026년 9월 29일)으로 대화 순서를 맞춘다. 여러 장이면 시간순으로 이어 붙여 해석한다.
- 캡처 속 메일·문서 사진처럼 작은 글씨는 해당 영역만 잘라 4~7배 확대해 읽는다.
- '전체보기'로 잘린 긴 메시지는 다른 캡처나 파일에서 원문을 찾는다.

### 파일·시트
- Google Sheets는 요약 읽기가 일부 행만 보여줄 수 있다. 전체 행이 필요하면 CSV로 내보내 확인한다.
- PDF·PPT·XLSX는 텍스트를 추출해 핵심 수치(가격, HS Code, 인증번호, 유효기간, 마감일)를 뽑는다.

## 4. 내용 선별·교차검증

- **해당 업체 관련 내용만** 남긴다. 다른 업체 건, 수업·잡담, 개인 일정, 선물·이모티콘, GTEP 내부 홍보 같은 건 제외한다.
- 업체 톡방(외부)과 동료 대화(내부)를 구분해 기록한다. 내부 논의는 '■ GTEP 내부 논의' 묶음으로 분리한다.
- 각 사실에 날짜(M/D)와 주체(업체 담당자 / 요원 이름)를 붙인다.
- 대화 중 정정된 사실(예: 바이어 이름 혼동)은 정정된 내용으로 쓴다.

서로 다른 자료가 같은 사실을 말하는지 대조한다. 자주 어긋나는 것:
- 인증·특허 표기 (회사소개서 vs 담당자 답변)
- 제품 규격·매수 (가격표 vs 시험성적서)
- HS Code (추정 vs 업체 회신)
- MOU·계약 상태 (체결 / 재체결 / 해지)
- 브랜드·바이어 소유 관계와 업체명 표기

규칙:
- 업체 담당자의 최신 답변이 문서 표기보다 우선한다. 충돌은 '애로 및 질의사항'에 적고, 이미 쓴 다른 섹션(제품 소개 등)도 함께 고친다.
- 근거가 없는 내용은 쓰지 않는다. 추정은 '(추정)', 미확인은 '확인 필요'로 표시한다.
- 이전 주 보고서에 틀린 내용이 있으면 고치고 사용자에게 알린다.

## 5. 항목별 기입 규칙

붙여넣은 양식의 각 칸을 캡처에서 파악한 내용으로 채운다. 각 줄은 `· [태그] 내용 (M/D)` 또는 `1. 제목` + `- 세부` 형식으로 쓰고, 서술은 명사형 종결(~함, ~완료, ~예정)로 짧게 쓴다.

| 항목 | 기입 기준 |
|---|---|
| 업무기간 | 2번 참고 |
| C/L 발송 횟수 | `주간 N회 / 누적 N회`의 N만 채운다. 근거가 없으면 주간 0회, 누적은 직전 주차 값으로 두고 사용자에게 확인. 회색 안내문은 지운다. |
| 정기업무 | 미팅, 자료 수령·송부, 서류 작성, 시트·양식 제작, 시장조사, 바이어 코레스, 교수님 보고 등 수행한 일 |
| 전자상거래 업무 | 플랫폼별(Qoo10, tradeKorea, Alibaba, 스마트스토어, Amazon 등) 진행 상황, 주문·배송·CS |
| 전시회 관련 | 양식의 `· 확정 전시회 :` `· 일정 :` `· 준비내용 및 진행사항 :` 뒤에 채운다. 없으면 '없음'. 수출상담회처럼 전시회가 아닌 건은 '해당 없음 — 대신 ○○ 신청'으로 쓰고 준비 과정은 하위 줄(`- `)로 정리. 참가를 마친 전시회는 Ⅳ. 연간 전시회 참가 계획 표에도 반영 |
| 주요 논의사항 | 업체와 합의·결정된 것, 업체 의견, 업무 방식. 이어서 '■ GTEP 내부 논의' 묶음에 선정 근거, 역할 분담, 빅플랜·우선순위 |
| C/L 발송 포맷 및 현황 | 양식의 `1. 총 발송 횟수` `2. C/L 발송 아이템` `3. Inquiry 문의`에 값을 채운다. 발송이 없으면 첫 줄에 '금주 C/L 발송 없음 (발송 포맷은 직전 주차와 동일)'. Inquiry 0회면 (1)(2)는 비운다. 캡처 삽입 안내문은 캡처를 넣었거나 해당 없을 때 지운다. |
| 다음주 업무계획 | To-Do·빅플랜 시트를 기준으로 프로젝트 → 상시 → 운영 순. 이번 주에 걸린 후속 조치를 맨 앞에 둔다. |
| 애로 및 질의사항 | 자료 미수령, 정보 충돌, 확정 안 된 코드·인증, 일정 리스크 |

공통:
- 회색·이탤릭 안내문(placeholder)은 내용을 채우면서 지우고, 채운 글자는 기본 서식(검정, 기본 크기, 기울임 없음)으로 되돌린다.
- 라벨, 고정 문구(`· 확정 전시회 :` 등), 표 구조·병합·배경은 바꾸지 않는다.
- 셀 안 마지막 빈 줄바꿈은 남긴다.
- `- `로 시작하는 하위 줄은 들여쓰기(시작 20pt, 첫 줄 12pt)를 준다.

### 작성일 규칙

- 월~금에 작업하면 그 주 금요일 날짜를 쓴다. 금요일에 작업하면 당일이다.
- 토·일에 작업하면 직전 금요일을 쓴다. 다음 주 보고서를 미리 쓰는 경우일 수 있으니 한 줄로 확인한다.
- 요일은 어림하지 말고 계산해서 확인한다. 헤딩에 적을 날짜가 금요일이 아니면 고친다.
- 문서에 이미 있는 이번 주 헤딩 날짜가 금요일이 아니면 금요일로 바꾸고 마무리 보고에 알린다. 지난 주차 헤딩은 건드리지 않는다.
- 예: 10/8(목)에 작업 → 헤딩 `2026. 10. 09 주간업무보고서`, 업무기간 `2026. 10. 03 ~ 2026. 10. 08`.

```python
from datetime import date, timedelta
d = date.today()                      # 작업일
wd = d.weekday()                      # 월=0 … 금=4, 토=5, 일=6
fri = d + timedelta(days=4 - wd)      # 월~금은 그 주 금요일, 토·일은 직전 금요일
assert fri.weekday() == 4
print(fri.strftime('%Y. %m. %d'))
```

## 6. 문서에 반영

### 페이지 시작 위치 (필수)

각 주차 보고서는 **새 페이지 맨 위**에서 시작한다. `YYYY. MM. DD 주간업무보고서` 헤딩이 페이지의 첫 줄이어야 하고, 헤딩과 표 첫 행만 앞 페이지 끝에 남고 나머지 표가 다음 페이지로 넘어가면 안 된다.

- 헤딩 문단에 '페이지 나누기를 앞에 추가'를 건다. Google Docs API로는 헤딩 문단 범위에 `updateParagraphStyle`을 보내 `paragraphStyle.pageBreakBefore: true`, `fields: "pageBreakBefore"`로 설정한다.
- 그 속성을 쓸 수 없으면 헤딩 바로 앞에 `insertPageBreak`를 한 번만 넣는다. 이미 페이지 나누기가 있으면 또 넣지 않는다(빈 페이지가 생긴다).
- 빈 줄(엔터)을 여러 개 넣어 밀어내지 않는다. 헤딩 앞에 남아 있는 빈 문단은 지운다.
- 문서의 첫 보고서는 이미 첫 페이지 맨 위이므로 나누기를 넣지 않는다.
- 다음 주용 빈 양식 블록도 같은 기준으로 새 페이지에서 시작하게 둔다. 양식 안의 내용은 건드리지 않는다.
- docx 등 파일로 작성할 때도 같다. 헤딩 문단에 '단락 앞에서 페이지 나누기'를 설정한다.

### Google Docs (편집 커넥터가 있을 때)

순서: 양식 재현(헤딩 + 빈 표 + 라벨·고정 문구·안내문·서식·병합) → 날짜 기입 → 각 칸 내용 기입 → 안내문 삭제·서식 정리 → 검증.

- 문서를 읽어 끝 위치와 대상 표의 셀 위치를 찾는다. 여러 위치를 고칠 때는 문서 뒤쪽부터 처리한다.
- 빈 표를 끝에 넣을 때: 헤딩 텍스트를 마지막 문단에 넣고, 헤딩 끝 위치에 `insertTable`(10행 2열)을 보내면 표 시작 인덱스 t는 '헤딩 끝 + 1'이다. 빈 표에서 (r, c) 셀의 문단 위치는 `t + 3 + 5r + 2c`이다. 셀마다 텍스트를 넣을 때는 마지막 셀부터 거꾸로 넣는다.
- 병합은 내용 기입·서식 적용이 끝난 뒤 마지막에 `mergeTableCells`로 한다(인덱스가 바뀌기 때문).
- 동료가 동시에 편집 중이면 requiredRevisionId 요청이 거절될 수 있다. 이때는 다시 읽고 targetRevisionId로 보낸다.
- 반영 후 다시 읽어 중복 붙여넣기, 누락, 서식 이상, 남은 안내문이 없는지 확인한다. 헤딩이 새 페이지 맨 위에서 시작하는지, 헤딩 날짜가 금요일인지도 함께 본다.

#### 문서가 커서 읽기 결과가 잘릴 때
누적 보고서 문서는 수백만 자가 되어 `read_doc` 결과가 앞부분에서 잘릴 수 있다. 이때는:
- **끝 위치 찾기**: 아주 큰 인덱스(예: 99999999)에 `insertText`를 보내면 거절되면서 오류 메시지에 'end index of the referenced segment, N'이 나온다. N-1이 마지막 줄바꿈 위치다. 요청 하나라도 실패하면 아무것도 반영되지 않으므로 안전하다.
- **위치 검증**: 확인할 요청 뒤에 일부러 실패하는 요청(큰 인덱스)을 붙여 한 번에 보낸다. 오류가 `requests[1]`을 가리키면 앞 요청은 유효하고, `requests[0]`을 가리키면 그 위치가 잘못된 것이다. 문서는 바뀌지 않는다.
- 표 끝 판별: 셀의 마지막 줄바꿈은 삭제할 수 없으므로 `deleteContentRange` 1글자 검증으로 표 끝과 일반 문단을 구분할 수 있다.
- 텍스트 확인은 Drive `read_file_content`로 하되, 이것도 끝이 잘리면 반영 결과를 직접 확인하지 못했다고 마무리 보고에 적고 사용자에게 화면 확인을 부탁한다.

### 편집 커넥터가 없을 때
사용자에게 공식 양식 링크에서 6번 항목의 주간업무보고서 양식 한 세트를 복사해 업체 문서 끝에 붙여넣으라고 안내하고(헤딩 앞 Ctrl+Enter로 새 페이지), 각 칸에 넣을 텍스트를 양식 행 순서대로 답변으로 준다. 맨 위에 금요일 날짜로 된 헤딩(`YYYY. MM. DD 주간업무보고서`)을 함께 준다. 커넥터를 켜면 문서에 직접 넣을 수 있다고 한 줄로 안내한다.

## 7. 마무리 보고

사용자에게 다음을 짧게 알린다.
1. 양식 붙여넣기·날짜 기입 결과 (헤딩 날짜, 업무기간)
2. 항목별로 반영한 핵심 (한두 줄씩)
3. 고친 기존 내용과 그 이유
4. 제외한 내용
5. 확인이 필요한 부분 (미확인 사실, 자료 간 충돌, 추정, 원본 양식과 기준 구조가 달랐던 점). 페이지 시작 위치나 반영 결과를 직접 확인하지 못했으면 여기에 적는다.
